## 0. The owner's three answers (2026-09-26, before anything was built)

1. **postinstall makes the `hotserve-backup` account too, identically**: the one `useradd` line setup uses (`--system --no-create-home --home-dir /nonexistent --shell /usr/sbin/nologin`), when the account is missing, as it already does for `hotserve`; setup keeps making it when missing (the by-hand path, the e2e box). Never removed on purge. The deferred check — an account made wrongly by hand is *refused*, not normalised — is 4c's.
2. **The hourly timer: `OnCalendar=hourly`, `RandomizedDelaySec=10min`, `FixedRandomDelay=true`, `Persistent=true`.** One per-box offset, so the interval stays an hour and a fleet does not hit one storage at :00; a box that was off runs at boot. Sunday's 03:00–03:10 run has twenty minutes before the 03:30 drill.
3. **A failed drill is the service's failure too**: `drill` keeps exiting 1 when an app's restore was not proven or the drill could not begin, so `hotserve-backup-drill.service` is `failed` in `systemctl --failed` until the next drill succeeds; the record and `status` say the same. The same rule the hourly run has (exit 1 when not every app was backed up). Nothing acts on it: no `OnFailure=`, no restart. Consequence taken as-is: a run that finds the drill holding the lock exits 1, so `hotserve-backup.service` is red for that hour (below, decision 6: the drill waits for a run instead, by `After=`; the reverse is not ordered).

## 4. Decided by me, the owner's to overturn (each in the PR body under "For the owner", and in `PLAN-backups.md`)

1. **`ConditionPathExists=/etc/hotserve-backup/repository.env` on both services**, not only the run's refusal: the timers are enabled by the package, and without the condition every hour on a box that has not run `setup` would be a red unit. The condition skips the start (not a failure), the timer keeps ticking, and the run's refusal stays behind it for the file vanishing between the check and `begin`.
2. **The hardening set** of §1 on both services, identical; measured, not reasoned (M54, M55). `ProtectSystem=` and its kin are deliberately absent, said in the unit file: each would hide the engine's mounts from the manager [M22].
3. **`TimeoutStopSec=3min`, `TimeoutStartSec=infinity`** (explicit; oneshot's own default is infinity, and D4 says no unit has a time cap): a `systemctl stop` gives the run its two minutes to stop its own units by name and confirm them gone before the manager's SIGKILL, after which `BindsTo=` ends them.
4. **`After=network-online.target`, `Wants=network-online.target`** on both: a `Persistent=` catch-up at boot otherwise starts restic before the network is up, and a run whose repository is unreachable is a red unit for nothing.
5. **The run under the timer refuses a missing `restic`/`sqlite3`/`hotserve` with setup's own words** (`open` shares setup's program check) rather than a unit's 203, if M59 shows the latter.
6. **The drill waits for a run (`After=`); a run does not wait for a drill.** A mutual `After=` is an ordering cycle in any transaction that holds both (`systemctl start a b`). The drill is weekly and a missed one is a week without proof (old after 8 days); the hourly run's loss is an hour. Decision 3's consequence stands for the run.
7. **Purge keeps `/etc/hotserve-backup/` (the brief) and removes only what is the package's own**: the cache, the record, the id, `listing.err`; `staging/` and `restore/` by `rmdir` (a directory that is not empty is named and kept: copies of an app's data a killed run left are not root's to delete). Says each thing it kept.
8. **`validate` and the run: a `{$NAME}` root is refused only where an app declares a backup** (the owner's own recommendation, 4a): with none declared the plan's root is left empty and nothing is said of it; `bin/push` on a box without backups stops refusing configs that work today. The other refusals (an opaque variable in an import, an empty glob) stay: they hide apps.
9. **`status`'s "set up" stays the credential file's mtime**, not the id file's presence: the id file is written by setup alone, so a by-hand file (`rest:`, `gs:`, `swift:`) would have no "set up" time and `status` would exit 3 for ever. With the timer, the first run comes within the hour and ten minutes of setup, so a re-run of setup restarting the 3-hour grace on a box that has never run is harmless. Nothing changes; said here so the brief's question has an answer.
10. **The `hotserve` package carries `hotserve-backup`** (4a's plan: "once 4c ships the binary in hotserve's own package"): one `.deb`, `/usr/bin/hotserve-backup` `0755`, the four unit files `0644` under `/lib/systemd/system`, `Recommends: restic, sqlite3`. The raw-binary tarball (release.yml) is left as it is — for the owner: whether it gains `hotserve-backup` and the unit files.
11. **The docs run literally in the install-test smoke, extended**, not a suite of their own: it is the one lane that installs the real `.deb` under real systemd on both architectures, which is what "a fresh box" means. An `admin` account in `sudoers` runs the README's commands under `script(1)`; the repository is `rclone serve s3` in the same container, the static binary copied into the smoke image from the same pinned `rclone/rclone` image the e2e fixture uses (Debian's rclone has no `serve s3`).
12. **The e2e box installs the unit files and runs postinstall, then removes the account and the timers' symlinks** so that the setup suite still shows setup making the account, and no timer fires into a suite (a run from the timer would take the lock from under a scenario). The units suite starts the services by hand.
13. **setup's closing `next:` line names the timer** ("the first backup runs within the hour and ten minutes: `systemctl list-timers hotserve-backup.timer`; to run one now, `sudo systemctl start hotserve-backup.service`"), where 4b said nothing runs on a schedule.
14. **postinstall warns of an existing `hotserve-backup` account with a login shell or a real home**, and changes nothing; setup refuses it (the deferred check, built). A new limit: a box whose account was made by hand with a shell cannot run setup until it is fixed — the message gives the `usermod` lines.
