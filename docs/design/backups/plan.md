# Backups for hotserve — design plan (for review, before any code)

Sources: `main` at f6919df and `HANDOVER-backups.md`. Nothing else.
Order of this document: what I measured first, the privilege boundaries,
the failure modes ruled out, then the shape that follows from them, the
PR sequence, what is still unmeasured, and the decisions I need from you.

Legend: **[H]** measured in the handover · **[M]** measured by me on
2026-09-19 (Debian 13.6, systemd 257.13, restic 0.18.0, sqlite3 3.46.1,
systemd-in-Docker, arm64 — the same kind of container CI uses) ·

## 0. Measured first

| # | Question | Result |
|---|---|---|
| M1 | `sqlite3` on a FIFO (handover: not measured) | **Blocks forever**: reading a table, `VACUUM INTO`, a `mode=ro` URI — and **`select 1` too** (the shell opens the file itself before any SQL). The busy timeout does not bound it. `/dev/null` opens as a *valid empty database*, exit 0. A symlink to a non-database exits 26. → The file-type check has to happen before `sqlite3` is ever started, in our own code, and "opens fine, zero tables" is not evidence of a database. |
| M2 | `LoadCredential=` (handover §6: not measured) | In systemd-in-Docker, PID 1 logs the credential mount as succeeded and `$CREDENTIALS_DIRECTORY` is set, but the directory **does not exist inside the unit** — with or without a sandbox, as root or not. Adding `/run` to the view fails the unit 217. → A mechanism the project's own test lanes cannot exercise. **Not used.** Credentials reach a unit through `EnvironmentFile=` [H: read by PID 1 as root; file stays root-only]. |
| M3 | Who should hold the credential: uid `hotserve` in a user namespace, or another uid? | A **dedicated uid** (`hotserve-backup`), *no* user namespace, `AmbientCapabilities=CAP_DAC_READ_SEARCH` (bounding set the same, one capability), inside `TemporaryFileSystem=/:ro` + the base view: the unit starts (no 217/USER), reads a `0600 hotserve` file, cannot write it, sees no `/etc/shadow`. From outside, **uid `hotserve` gets EACCES on its `/proc/<pid>/environ` and `/proc/<pid>/root`, and EPERM on `kill`**. Same-uid + `PrivateUsers=yes` [H] closes the reads but leaves signals. |
| M4 | Snapshot paths vs. the liveswap root; symlinked root | App data bound with `BindReadOnlyPaths=<root>/<app>/shared:/backup/<app>/files`, through a **symlinked root**: the snapshot holds the *data* (the mount resolves the link) under `/backup/blog/files` — **the same path on every box, whatever `root` is**. Closes two [H] pitfalls by construction. |
| M5 | Special files under restic | A FIFO and a symlink in the source do not block restic; both are stored as nodes and **recreated on restore** (`trap.fifo`, `link -> /etc/passwd`). `total_files_processed` counts regular files only. |
| M6 | Restore as the dedicated uid, no capabilities, no user namespace | **Exit 0**; every file is owned by the restoring uid (restic overlooks the EPERM from `lchown`). No EINVAL, so a rebuilt box with another uid number for `hotserve` does not turn every file into an error. |
| M7 | "Nothing to restore" | `restore <id>:/backup/shop/files` (absent path) → **exit 1**, "not found". `restore <id> --include /backup/shop` (matches nothing) → **exit 0, "Restored 0 files"**. → Only the `<id>:<path>` form is used, and the count is checked as well. |
| M8 | A killed orchestrator and its transient units | A transient unit started with `BindsTo=<orchestrator>.service` is **stopped by PID 1 when the orchestrator is SIGKILLed** (a `Type=oneshot` in `activating`). Adding `After=` as well deadlocks: the child waits for a oneshot that never finishes activating. → `BindsTo=` alone. |
| M9 | Do awkward paths and `${VAR}` survive a unit's properties? | Over **D-Bus with typed properties** (what liveswap's runner already does for binds): a bind source of `/srv/live swap:50%$HOME/blog/shared` mounts and reads correctly — the struct is never split or expanded. The same path through `systemd-run -p BindReadOnlyPaths=` is refused ("Unknown options"). Argv: `ExecStartEx` with `no-env-expand` delivers `${SECRET}` literally; plain `ExecStart` (what go-systemd's `PropExecStart` sends) delivers **the secret's value**. → The orchestrator speaks D-Bus, and builds `ExecStartEx` itself. |
| M10 | What does restic 0.18.0 do about a stalled request by itself? | It has `--stuck-request-timeout` (default **5m**): a request moving no data is retried. With the ~15 min retry ceiling [H], restic bounds its own waiting; nothing outside it has to. |
| M11 | restic's exit status when files **vanish mid-backup** (4000 files, the last 1500 removed after restic reported 246 done) | **Exit 0, no error line on stdout or stderr**, summary `files_new: 2499`. restic leaves a vanished file out and says nothing. → `incomplete` (exit 3) is not routine on a live uploads dir, so status can treat it as a real fault. It also means exit 0 says nothing about *which* files are in the snapshot: the per-item `ls` check (failure mode 14) is what stands between a declared path that disappeared and a green run. |
| M12 | What `backup --quiet --json` writes | Exactly **one line, the summary**, on a clean run. Without `--quiet`: status lines (77 for 1 GiB) then the summary. Errors, when there are any, are further lines of `message_type: error`. |
| M13 | `restic init` as setup's probe, against the `rclone serve s3` fixture | Good key, new bucket: exit 0 in 2 s. **Wrong secret: exit 1 at once** ("signature … does not match"), whether or not the repository exists. Good key, existing repository: exit 1, "config already initialized". So init separates *wrong key* from *exists* by text only — both exit 1 [H] — but it does answer in seconds. |
| M14 | The view unit B is given | A declared sub-path binds where its parent is not (`…/shared/uploads` at `/backup/blog/files/uploads`): systemd makes the mount points inside the tmpfs. With `files .`, the live database and its sidecars masked by `InaccessiblePaths=-<path>`: `app.db` and `app.db-wal` read as **empty, mode 0, root-owned**; the two sidecars that do not exist are skipped by the `-`; **nothing is created in the app's real directory**. Fails closed — live database bytes cannot reach the repository — at the cost of an empty `app.db` in the snapshot's `files/`, so restore skips declared databases there, and each snapshot carries its own plan to say which those were. |
| M15 | How a **wrong S3 secret** ends ([H] stopped watching at 10 min) | `restic cat config` retried 19 times over **864 s**, then **exit 1** with "Is there a repository at the following location?". It does end by itself — D4's first trigger does not fire — but the ending names the wrong cause: not 12, not 10, and the text points at a missing repository. → A run's exit 1 is reported as "unreachable, refused by the storage, or other — see the journal", never as "no repository"; and `restic init` is **not** used as a fast probe outside `setup`: on a routine run it would answer a wiped bucket by quietly creating a fresh, empty repository. |
| M16 | `DynamicUser=yes` with `TemporaryFileSystem=/` | **The whole host filesystem stays in the view** — `/etc/shadow`, `/root`, `/home`, `/var/lib`, `/run/dbus` all present; with `User=` or as root, none are. Found by the unit package's own view test on its first run. → No `DynamicUser=` anywhere; `unit.Spec` has no field for it. Unit **P** runs as `hotserve-backup` inside user and PID namespaces instead (it holds no capability, so it can): not `hotserve`, because `/etc/hotserve` is bound for the Caddyfile's imports and the apps' `*.env` files there are `root:hotserve 0640`. The view test runs for every way a Spec can say who runs the command. |
| M17 | What a private network namespace and the view hold besides what is named | `/run/systemd/incoming` (the manager's mount-propagation directory, closed to the unit) and nothing else of `/run/systemd`; the network namespace holds `lo` and the kernel's nine fallback tunnel devices, and **no routes** — so "no network" is asserted on routes, not on interfaces. |
| M18 | Is there a way to run `sqlite3` that cannot block on a FIFO? (the owner's question) | **No flag does it** — plain, `-readonly`, `.open --nofollow`, `-deserialize` and a `mode=ro` URI all block: the *shell* opens the path read-only to look at its type before SQLite does. **`sqlite3 :memory: "ATTACH 'file:<path>?mode=rw' AS src; VACUUM src INTO …"` does**: the shell never opens the file, SQLite opens it read-write (which does not block on a FIFO) and fails on its first read — FIFO and link-to-FIFO exit 10, directory and socket exit 14, **all within 2 ms**. `mode=rw` also means "do not create": an absent path is exit 14 and nothing appears in the app's directory, where a plain `ATTACH` *creates an empty `app.db` there* and copies it, exit 0. Works on a live WAL database at a path holding a space, `%`, `#` and `?` (percent-encoded). → The dump uses this form. *(The conclusion first drawn here — that the bound could go — was wrong: see M19.)* |
| M19 | **Correction to M18**, measured as uid `hotserve` rather than root | A FIFO the app has made **read-only (mode 0400) still blocks the `ATTACH … ?mode=rw` form for ever**: when the read-write open is refused, SQLite retries read-only, and that is the open that waits. (Mode 0644: exit 10 in 3 ms. Mode 0000: exit 14 in 4 ms. A read-only *database* copies fine.) M18 was measured as root, which ignores mode bits. So the swap is **not** closed by construction, and "no bound anywhere" does not stand. What *is* measured: the copy's **target file appears 11 ms after sqlite3 starts, whatever the database's size** (300 MB: target at 11 ms, copy done at 456 ms), and **never** when the open is blocked. Resource use of the two forms is identical (427 MB database: direct 1.04 s, ATTACH 0.85 s; peak RSS 7.6 MB both). |
| M20 | Where `sqlite3` waits for a **locked** database, relative to creating the copy's target | **Before.** With the source held `BEGIN EXCLUSIVE` for 3 s, the target appeared only when the lock was released (I had believed the reverse; the test written to pin it said otherwise). So "no target yet" is either a blocked open or an honest lock wait of at most `busyTimeout` (30 s) — and the open bound must exceed that. **Owner-approved design: `openWithin` = 5 min, on the target's *appearing* only; once it exists nothing bounds the copy.** Tests: a real mode-0400 FIFO under a real `sqlite3` run as `hotserve` → killed at the bound, next database dumped; the lock ordering pinned (fails if a later SQLite creates the target first); `openWithin ≥ 2 × busyTimeout`; the watcher against a stand-in process whose copy outlasts the bound threefold → left alone. |
| M21 | Can an app aim its backup at a sibling's data? (found in self-review of PR 2, before anything was pushed) | **Yes, as first written.** A bind source is a path PID 1 resolves as root, following links, and an app's declared path is the app's own to replace while it runs: with `blog/shared/uploads -> ../../shop/shared`, the upload unit — which reads any file it is shown — **read shop's 0600 file**, and it would have gone into blog's snapshot and come back to blog on a restore. Checking first and binding afterwards only moves the race. **Fix, measured:** root opens `<root>/<app>/shared` and each declared path with `openat2(RESOLVE_BENEATH\|RESOLVE_NO_SYMLINKS\|RESOLVE_NO_MAGICLINKS)`, `O_PATH` (names the file, cannot read it), and gives the manager `/proc/<pid>/fd/<n>` as the bind source — after the name was swapped for a link to the sibling, the unit still saw the directory that had been opened. A link anywhere in a declared path is refused ("declare the real path"); the liveswap root itself may still be an alias. New e2e scenario 4b, seen failing against the unfixed engine (blog `ok`, shop's files in its snapshot) and passing after. *(The mechanism described here was not enough: see M22.)* |
| M22 | **Correction to M21**, from the independent review of PR 2 | Handing the manager `/proc/<pid>/fd/<n>` does **not** close the race: systemd does not follow that link, it reads its *text* and walks the path again. Deterministic proof: a pinned directory that was then deleted could not be bound (226/NAMESPACE, "No such file"). Under a real toggler flipping the name between the directory and a link to the sibling's while units start, that approach showed **8 of 200 units the sibling's directory** (and 153 could not start). M21's "measured" was a sequential swap, which both behaviours pass. **Fix, measured under the same toggler:** the engine binds the pin itself — `mount(2)` from `/proc/self/fd/<n>`, which the *kernel* follows to the very directory that was opened — onto a mount point in the run's own root-only directory, and gives the manager that path, which no app can touch: **300 units, 514,939 flips meanwhile, 0 shown anything but the app's own directory; no mount left behind.** The run takes its mounts away as it goes, and a run's sweep takes away (deepest first) any a killed run left. **For PR 4:** the run's service needs `CAP_SYS_ADMIN` and must share the host's mount namespace (no `PrivateMounts=`), or the manager cannot see the mount points. |
| M23 | `openat2` inside a unit (found by the e2e suite after a review fix used it in the dump unit) | **`RestrictSUIDSGID=yes` alone makes `openat2` return ENOSYS** inside the unit ("function not implemented"); the other filters used here do not. systemd's filter cannot look inside the struct `openat2` takes, so it refuses the call outright. The unit lane could not see it — it does not run inside a unit. → `backups/nofollow` walks a path one component at a time with `openat(O_NOFOLLOW)`, each relative to the descriptor before it — the same guarantee (no link anywhere, nothing leaves the directory, no name walked twice), no special syscall — and both the dump unit and the engine's pins use it, so **PR 4 may harden the run's own service with `RestrictSUIDSGID=` without breaking pinning.** |
| M24 | restic exclude files and awkward names | restic reads each line as a pattern and expands `$VAR`. With `\\`, `*`, `?`, `[` backslash-escaped and `$` doubled, five exact names (`app*.db`, `da[t]a/…`, `$HOME_SECRET.db`, `back\\slash.db`, `q?.db`) were excluded and their look-alikes (`appX.db`, `leaked.db` — the variable's value — `qZ.db`) stayed. The upload unit gets a root-written exclude file for declared databases inside `files` paths, behind the masks: a mask covers only what exists when the unit starts. **The mask's empty stand-in file is therefore no longer in the snapshot** (it is excluded too) — restore need not skip it, though it still must never install anything over a declared database from `files/`. |
| M25 | What `restic restore --json` says (PR 3, before any restore code) | With `--quiet`, **one line, the summary**: `{"message_type":"summary","total_files":13,"files_restored":13,…}`. `total_files` / `files_restored` count **every entry** — directories, FIFOs and links too (7 files + 4 dirs + 1 FIFO + 1 link = 13). **A field that is zero is left out**: `--include` matching nothing prints `{"message_type":"summary"}` and exits 0. `<id>:<absent path>` → exit 1, `{"message_type":"exit_error","code":1,"message":"path backup/ghost: not found"}` on stdout; a single file → exit 1 "not a directory" [H]. A backup of a *relative* target (`backup/blog`) stores `/backup/blog/…`, so the ls test's paths are real. → The fetch verdict: exit 0 **and** a summary **and** `files_restored` present, > 0 and equal to `total_files`. Pinned by `TestIntegrationResticRestoreSaysWhatItRestored`. |
| M26 | R2 with `CAP_CHOWN` alone, as §1.3 had it | **Does not work**: root without `CAP_DAC_READ_SEARCH` is "other" to a 0700 directory of `hotserve-backup`'s — `chown: cannot read directory: Permission denied`, exit 1. With `CAP_CHOWN` + `CAP_DAC_READ_SEARCH`: exit 0, tree, FIFO and link chowned, the link's target (`/etc/passwd`) untouched (`-h`). → **§1.3 R2 is two capabilities**, in a view of one directory, no network; it runs `/usr/bin/chown` and nothing of ours. |
| M27 | The copy `VACUUM INTO` makes, and `.restore` | The copy is in **rollback mode** (header bytes 18, 19 = 1, 1) whatever the source's, so it reads from a read-only mount; `?immutable=1` reads it too, with no lock and no `-shm`. `sqlite3 :memory: "ATTACH 'file:<live>?mode=rw' AS dst" ".restore dst 'file:<copy>?immutable=1'"` **under a writer looping inserts into a WAL database: exit 0, the snapshot's rows, the writer saw no error, journal mode still `wal`.** Target absent: exit 14, nothing created. Source absent: exit 1. |
| M28 | `.restore` into a live database with damaged pages (the usual reason to restore) | Pages past the first overwritten with noise (`integrity_check`: "malformed (11)"): `.restore` **exit 0**, then `ok` and the snapshot's rows. (A first page that is noise is not a database to sqlite3: the restore says to move it aside, and an absent database gets the copy put in place.) |
| M29 | Does the install unit follow a link the app swaps in? (raced: `uploads` and `app.db` flipped between the real thing and a link to a sibling's, 300 real units, ~530,000 flips) | **Files: never** — directories are opened one component at a time without following (`nofollow`), files land beside their name and are renamed onto it. **The database: sqlite3 opens it by name**, and with the sibling *deliberately put in the unit's view* the test **fails** (the sibling's database restored over, within 300 units). With the engine's real view — the pinned `shared/` and what was fetched, nothing else writable — 0 of 300. → For the database the *view* is the protection, and `TestWhatEachRestoreUnitIsGiven` pins what the view holds. |
| M30 | Ctrl-C on an operator's command (D4 leans on it) — found by restore e2e 13, **and true of `run` as merged in #139** | go-systemd closes a connection when the context it was made with is cancelled; `main` made it with the signal's context. After Ctrl-C: "the unit could not be confirmed gone … use of closed network connection", **the unit ran on**, and the unit that removes plaintext could not start. The integration test for cancelling built its runner with `context.Background()` and cancelled another context, so it passed. → `NewSystemRunner` connects with `context.WithoutCancel(ctx)`; `TestIntegrationARunnerOutlivesTheContextItWasMadeWith` (seen failing without the fix), backup e2e 10b, restore e2e 13. |
| M31 | Odd entries through a real fetch unit (raised by the independent review): a setgid directory, a setuid file, a hardlinked pair, a unix socket, a 0555 directory, a mode-0 file — all in one `uploads/` | **The fetch is fine**: exit 0 under `RestrictSUIDSGID=yes`, and `files_restored == total_files` with the socket and the hardlinks in. **What broke was removing it**: `os.RemoveAll`, as the owner, cannot empty a 0555 directory → the unstage unit exits 1, the plaintext stays, and every later restore and drill of that app stops at "emptying … before the restore". → `clean` opens every directory (chmod 0700, by lstat) before it removes; restore e2e seeds a 0555 directory and a 0755/0644 pair into every snapshot. |
| M32 | A lock met by `.restore` itself (review: from the shell's source, unmeasured) | Writer holding `BEGIN EXCLUSIVE` from the start: `PRAGMA dst.schema_version` fails, **exit 5**. Reader holding a shared lock on a rollback-journal database: the pragma passes and `.restore` fails with **exit 1, "Error: source database is busy"** — a dot-command's failure is always 1. → `RestoreOver` takes that exact line (it holds no path) as busy too; `TestIntegrationRestoreOverALockedDatabaseIsBusy`, both shapes, database unchanged. |
| M33 | `restic stats --mode restore-size --json <id>`, for a free-space preflight (owner: yes, 2026-09-20) | One line: `{"total_size":10000002,"total_file_count":8,"snapshots_count":1}`; the size **equals what the restored tree takes** (`du`), a hardlinked file counted once. **An id the repository does not hold: exit 0, `{"total_size":0,"snapshots_count":0}`**, the complaint on stderr only — so only `snapshots_count == 1` is an answer. And without a preflight, measured on an 8 MiB filesystem under the fetch directory: restic fills it and **exits 1**. → `room` runs before every fetch (restore, drill, the first-backup drill); e2e 13b, seen failing first (a fetch unit was started, the disk filled). |
| M34 | `SystemCallFilter=~open_by_handle_at` (owner: measure, then implement — 2026-09-20): does it break restic or chown, and does it bite? | Measured in real transient units. **restic** init, backup, `check --read-data`, restore: exit 0 with the filter. **`chown -hR`**: exit 0. **The syscall** (a probe calling `open_by_handle_at` with a bogus handle): off the filter the kernel answers (ESTALE); behind `SystemCallFilter=~open_by_handle_at` + `SystemCallErrorNumber=EPERM` (measured with a distinctive ELIBBAD) the filter answers first. The container overlay does not export file handles, so the full CVE-2014-5277 chain is not runnable here — the syscall reaching the filter is what is pinned. -> emitted for **every unit that holds `CAP_DAC_READ_SEARCH`** (upload from #139, hand-over), coupled to the capability in `unit.properties`; `TestOpenByHandleAtIsDeniedExactlyWhereTheCapabilityIsHeld`. |
| M35 | Hardlinks, setuid/setgid bits and xattrs through a real `restic restore` (self-review of the author's own doubts, 2026-09-20) | A hardlinked pair comes back as **one inode with two names**, and restic counts **both names** in `total_files` and `files_restored` (7 = 7), so `fetchedAll` holds; but `stats --mode restore-size` and `bytes_restored` count the data **once** — and the install copied it once per name, so `room` under-estimated a hardlink-heavy tree and the names came apart. → the install now gives the file its other names with `linkat` (test: three names, one inode). **setgid 2755 on a directory and setuid 4711 on a file come back from restic** (outside a unit); the install masks to 0777 and the unit has `RestrictSUIDSGID=`, so they are not put back — now said in the README, with xattrs/ACLs and directories' times. (No `setfattr` in the image: xattrs unmeasured, and dropped by `copyFile` by construction.) |
| M36 | sqlite3 and a path over its unix VFS limit (the path-length limit the owner chose to bound, 2026-09-20) | **Not refused: replaced.** A database path of 513 bytes (components of 8, well under NAME_MAX 255) — `sqlite3 <path>` cannot open it ("unable to open database file"), but `ATTACH 'file:<path>?mode=rw'` **succeeds**, `database_list` shows `src` with an **empty filename** (a temporary database), and `integrity_check` says `ok`. At 504 bytes everything works. So `mode=rw` on an over-long path is a dump of nothing that checks out, and a restore of nothing over what is there. Not reachable through the engine — an app's own path (`/var/lib/liveswap/<app>/shared/…`) is longer than any unit's (`/shared/`, `/restore/sqlite/`), so no database an app could open sits past the limit — only through a hand-made snapshot. → `dump` refuses a path over 480 bytes before sqlite3 sees it, in every place one is handed over (`run`, `CheckCopy`, `RestoreOver`), as its own error; and **the declaration is bounded in `backupdecl`** (PR of its own). |
| M39 | `restic init` 0.18 as `hotserve-backup` in a real unit, against the fixture (PR 4b, 2026-09-26) | `--json`: **one line on stdout**, `{"message_type":"initialized","id":"<64 hex>","repository":"…"}`, exit 0, ~2 s. A repository that exists: **exit 1 at once**, stderr one JSON line `exit_error` whose message ends "repository master key and config already initialized" against the fixture and **"config file already exists" against a local path** (found by the integration pin: two wordings, one condition — restic's `Stat` of the config answers on a local path and on S3 proper, and does not on the rclone fixture, where init goes on to find the config as it makes the key) — **whatever the password**, so init cannot tell a wrong password from a right one on an existing repository; `repositoryExists` takes either wording. Wrong S3 secret: exit 1 at once ("signature … does not match"). A host that does not resolve, a port nobody listens on, HTTPS to an HTTP server: **exit 1 at once** — `init` does not retry [where `cat config` does, M15]. A host that swallows packets (10.255.255.1): exit 1 after **30 s** (dial i/o timeout). A storage that takes the connection and never answers (`systemd-socket-activate -l 127.0.0.1:9999 /bin/sleep 3600`): no answer for as long as watched — restic's own stuck-request timeout is 5 min. → setup's units get a 2-minute clock, with "still waiting" at 20 s; the clock is for the last case only. |
| M40 | `restic cat config --no-lock` as the probe of an existing repository | Right password: exit 0, the config JSON with `id`. Wrong password: **exit 12 in ~1 s** ("wrong password or no key found"). No repository: exit 10. `rest:` against an S3 server (HTTP 400): retried for minutes — the probe runs only after `init` has said the key opens the storage. |
| M41 | How PID 1 reads `EnvironmentFile=`, every shape a hand might write (a unit running `/usr/bin/env -0`) | Key whitespace **trimmed**; surrounding `"`/`'` **stripped**, an unterminated leading quote too; the **last** assignment wins; a line whose first character is `#` or `;` is a comment; a line with no `=` is skipped; a trailing `\` joins the next line; outside quotes **a backslash escapes the next character** (`a\b\\c` → `ab\c`); inside double quotes only `\\` and `\"`; `$`, `#`, `;`, `%` and a tab inside a value are kept; trailing whitespace trimmed; **a quote runs on to the line that closes it (`MULTI="one` / `two"` is `one⏎two`), and one that is never closed takes the rest of the file** — found by the pin: the first, by-hand reading printed a value holding newlines as if it were several variables, and everything it "read" after `LEADQ="abc` was inside that value. → `envfile.Parse` mirrors all of it and is pinned to a real unit by `TestIntegrationSystemdReadsAnEnvFileAsParseDoes`; the lint says of a quote never closed that the manager reads the rest of the file as that value; the writer writes plain `KEY=value`, doubles a backslash, and refuses a line break, a control character, whitespace at either end and a leading quote. |
| M42 | `useradd --system …` on an account that exists | Exit 9, "already exists"; setup looks first and never runs it then. `useradd` in the container allocates from the system range (995). |
| M43 | A terminal for the e2e suite | `script` is in `bsdutils` (Essential): `script -qec "<cmd>" /dev/null` with the answers on stdin. A pty echoes what arrives **before** echo is off, so a secret is sent 2 s after the key id; the key id, typed with echo on, must show in the capture or the "not shown" check is vacuous. |
| M44 | Which backends Debian's restic 0.18 has, and their variables | `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`, `B2_ACCOUNT_ID`/`B2_ACCOUNT_KEY`, `RESTIC_REST_USERNAME`/`RESTIC_REST_PASSWORD`, `GOOGLE_PROJECT_ID`/`GOOGLE_APPLICATION_CREDENTIALS` (a file), `OS_*` for swift. **No `AZURE_*` at all: `azure:` is "invalid backend"** — Debian builds restic without it. → setup asks for s3, b2 and rest; refuses azure; leaves gs and swift to the file by hand. |

## 1. Privilege boundaries

### 1.1 Principals

| Principal | Trust | Note |
|---|---|---|
| root / PID 1 | TCB | |
| Operator with sudo | TCB | Runs `setup`, `restore`. |
| `hotserve-admin` group | **hotserve's reach, not root's** (examples/box/sudoers) | Writes the Caddyfile. So *the Caddyfile is not root-trusted input*. |
| uid `hotserve`: the serving process, its user manager | Attacker-facing (T4/T5) | First thing the internet reaches. Holds every app's data already. |
| App code (T1) | Hostile | Chooses the bytes, names and file types in `shared/`, including the SQLite file `sqlite3` will parse. |
| uid `hotserve-backup` (new) | Holds the repository credential while a job runs | Runs restic and nothing else. No login, no home, no files of its own but the restic cache. |
| Storage provider | Holds ciphertext | Enforces the no-delete key. Not tested [H decision]. |
| Off-box pruning machine | Holds the second key | Out of the box's sight. |

### 1.2 The rules everything below follows

1. **App data is read and written by uid `hotserve`, or read-only by
   `hotserve-backup` through one capability in a view that contains only
   that app.** Root never opens, parses, copies or deletes app data. (One
   bounded exception: §1.4 R2.)
2. **Whatever parses app-controlled bytes (`sqlite3`) holds no credential,
   has no network, and sees one app.** Its sandbox is the app's own.
3. **The credential exists in two places: a root-only file, and the
   environment of a restic process running as `hotserve-backup`.** Never in
   argv, never in the orchestrator, never under uid `hotserve`.
4. **Root consumes nothing from the serving process.** Not the admin API,
   not a socket, not a file the `hotserve` uid can write.
5. **The serving process gains no code that runs**: a parsed, validated,
   inert declaration — no goroutine, no timer, no exec, no socket.
6. **No operator- or app-chosen string reaches a unit's argv, and none is
   ever parsed by systemd.** Argv is constants and an app name matching
   `^[a-z0-9-]{1,63}$`, sent as `ExecStartEx` with `no-env-expand`; the one
   operator string in a property, the liveswap root, travels as a typed
   D-Bus struct that systemd neither splits nor expands [M9].

| Attacker | Gains |
|---|---|
| T1, app code | Its own data, as before. A crafted database reaches `sqlite3` in unit A: own `shared/`, no network, no credential, no sibling. A planted FIFO/socket/device/symlink is refused before `sqlite3` starts [M1] and reported, never restored into place [M5]. |
| T5, the serving process | Nothing new. It cannot read B's environment or signal it [M3], cannot start system units [H], and nothing root reads is its to write. It can corrupt live data (already true) — which is what the no-delete key and off-box retention are for. |
| `hotserve-admin` | Can choose what is backed up within uid `hotserve`'s reach. Cannot obtain the credential, cannot become root. |
| A stolen storage key | Bounded by the provider's no-delete policy — the provider's job, untested, and **the box never claims otherwise** (no "can this key delete?" probe: [H] predicts it answers wrongly on B2). |

## 2. Failure modes ruled out

Each line: the failure → what rules it out. **(c)** = by construction,
**(t)** = by a check whose e2e test is written first and shown failing once.

**Credentials**
1. A credential in a process uid `hotserve` can read → dedicated uid [M3]. (c)
2. A credential expanded into argv by systemd (`${RESTIC_PASSWORD}` as a declared path [H]) → rule 6: `ExecStartEx` + `no-env-expand` on every unit [M9]; go-systemd's `PropExecStart` is never used here. (c)+(t)
3. A key with whitespace overriding the intended value → one writer; `status` lints with systemd's rules. (t)
4. A generated password shown after it has taken effect → order is *show → operator confirms it is stored → write the env file → `restic init`*. Interrupt anywhere: either nothing exists, or the file holds the password. (t: kill between each step)
5. A secret asked for, then failing on something knowable → preflight before the first prompt: root, restic, sqlite3, systemd, URL scheme, existing setup. (t)
6. `apt purge` silently removing the only copy of the password → maintainer script says so, loudly, first (decision D6).

**SQLite**
7. A live database copied as a file → declared databases go through `VACUUM INTO`; the files pass excludes them and their `-wal/-shm/-journal`. (c)
8. Busy database failing instantly → explicit `.timeout`. (c)
9. Root-owned `-wal/-shm` locking the app out → root never runs `sqlite3`; A is uid `hotserve`. (c)
10. A damaged copy passing → `integrity_check` verdict needs *both* exit 0 *and* output exactly `ok` [H: two failure shapes]. (t: both shapes)
11. FIFO / device / socket / symlink as a database → `O_NOFOLLOW|O_NONBLOCK` open + `fstat` regular file + SQLite header, before `sqlite3` [M1]. An empty file is "not a database". (t)
12. `VACUUM INTO` refusing an existing target, or a full disk → staging is emptied by C at the start of every run; "disk is full" is its own reported class, with the bytes needed.
13. Plaintext copies left behind → C runs after B on every path, and first thing next run; `BindsTo=` covers a killed run [M8]. (t: SIGKILL mid-run, assert staging empty after the next run)

**restic**
14. "A snapshot exists, so it worked" [H] → success = exit 0 **and** a parsed `snapshot_id` **and** every declared item found in *that* snapshot by `ls <id> <dir>` on the item's own parent [H: direct children only]. Exit 3 is recorded as `incomplete`, never `ok`. (t)
15. "The newest snapshot" → the id from this run's summary, never `latest`. (c)
16. A symlink to a data disk backed up as a link → the source is a bind mount [M4]. (c)+(t)
17. Paths tied to one box's `root` → fixed `/backup/<app>/…` [M4]; `--host` is a constant, so a renamed or rebuilt box stays in one retention group. (c)
18. Apps sharing a retention group → one snapshot per app, distinct paths, no `--stdin-filename`. (c)+(t: run the documented `forget` policy against two apps)
19. A check and a backup colliding (exit 11) → `--retry-lock` as a **flag** on every locking command [H: the env var is ignored]. (t)
20. A listing failing while `check` holds the repository → read-only queries use `--no-lock`. (t)
21. Exit 1 meaning both "damaged" and "unreachable" → a `cat config` probe before and after `check`; verdict classes are `unreachable / no repository (10) / locked (11) / wrong password (12) / incomplete (3) / damaged`; "damaged" needs both probes to pass. (t: a host that does not resolve)
22. Minutes of *silent* retrying on a missing bucket or wrong secret → setup answers through `restic init` (~3 s either way [H]); anything an operator waits on says what it is waiting for after 30 s, and that Ctrl-C is safe (25). restic bounds its own waiting [M10]. **No unit has a time cap** [H decision; D4 proposal]. (t)
23. Running uncached under root's HOME → `RESTIC_CACHE_DIR` set; restic never runs as root. (c)
24. `forget` "succeeding" against a refusing store → the box never runs `forget`. (c)

**systemd / lifecycle**
25. A unit left running after its starter died → `BindsTo=` the orchestrator [M8]; for an operator-run command, a signal handler stops the exact units it recorded, and the next run sweeps that list first. (t: a real process outliving its context — no fakes)
26. Stopping by name pattern, or `ExecStopPost=` doing work on success → neither is used; units are stopped by the exact names recorded. (c)
27. A unit name an app can also have → names carry `_`, outside the app-name alphabet (the sandbox probe's trick, runner_systemd.go). (c)
28. `--wait --pipe` hanging past a cancel → no pipes; results come from the manager and from files. (c)
29. Two runs interleaving (timer + operator) → one `flock`; the second says who holds it. (t)
30. `is-active` reading a running oneshot as failed → status reads `ActiveState`/`Result`, and knows `activating`. (t)
31. Root leaving root-owned files where a job must write → every restic/sqlite3 invocation, by hand or by timer, goes through the same units. (c)

**Looking at data**
32. A sandbox making a path look absent, read as "no data yet" → existence is decided by the orchestrator's own `lstat` on the real filesystem, before any unit. (c)
33. Any error treated as "not there" → only `ENOENT` means absent. (t)
34. "Missing" treated as "never deployed" for an app backed up before → absent + earlier snapshot in the record or repository = **error: data missing**; absent + none = `pending`. (t: delete `shared/` after a good backup)

**Restore and status**
35. A restore that restores nothing, exit 0 → `<id>:<path>` form [M7] + restored count against the snapshot's. (t)
36. Special files or links restored into place [M5] → R3 installs regular files and directories only; the rest is listed. (t)
37. Ownership by number on a rebuilt box → R2 [M6]. (t: restore onto a box whose `hotserve` uid differs)
38. "Fresh" from a record whose snapshot is gone → each run re-lists the repository and the record stores *when* each id was last seen there; status reports a vanished id as such. (t: delete the snapshot off-box)
39. A new setup flagged as failing → explicit `pending first run`, exit 0. (t)
40. "Backed up" logged when nothing was copied → the success line carries the snapshot id and what was verified in it; an app with nothing declared is never mentioned as backed up. (t)
41. **Nobody knows whether a restore works** → a restore drill: R1→R2→R3-check into scratch (never into place), on the first backup and then periodically; status says `restore last proven: <when>, snapshot <id>`, and exits non-zero when it is unproven or old. (D3)

## 3. The shape that follows

- **Declaration** (two lines per app, in the app's Caddyfile block; paths relative to `shared/`):
  ```
  app blog {
      backup {
          sqlite app.db
          files  uploads
      }
  }
  ```
  liveswap parses and validates it (local path, no placeholders, no overlap between items) so `hotserve validate` — and therefore `bin/push` — rejects a bad one. The type lives in a leaf package with no Caddy import, shared with `./backups`, along with the default root, so the two cannot drift.
- **`./backups`**: its own Go module and its own binary, `hotserve-backup`, which does not link Caddy — the root-equivalent process stays small, and "never part of the serving process" is literal.
- **Units**: static `hotserve-backup.timer` (hourly) + `.service`; a second timer for the weekly `check --read-data-subset=n/52` (n from the ISO week) and the drill, following the first with `Wants=`/`PartOf=` [H]. Enabled state handled by `dh_installsystemd`-style lines [H]; nothing starts until `setup` has run.
- **Repository backends**: those that take credentials from the environment — `s3: b2: rest: azure: gs: swift:` [H]. (D2)
- **Retention**: documented off-box recipe with the second key. The box never deletes.

### PR 2 — the engine, as it will be built

Written down before the code so it survives a long session; every item is a decision, with its reason.

**Layout.** `./backups` is its own Go module (`…/hotserve/backups`), added to `go.work`, the Makefile's `MODULES`/`PKGS`, CI's lint matrix and Dependabot. It requires the liveswap module for `liveswap/backupdecl` alone; that package is stdlib-only, so with module-graph pruning no Caddy requirement reaches `backups/go.mod` (checked when the module is created; if it does, `backupdecl` moves). Binary: `backups/cmd/hotserve-backup`. Not packaged until PR 4; the e2e box gets it by hand.

| Package | Does | Runs as |
|---|---|---|
| `unit` | Starts one transient **system** unit over D-Bus with typed properties and `ExecStartEx` + `no-env-expand` [M9]; `Type=oneshot`, so the start job ends when the command does and its result *is* the verdict — liveswap's `RunOnce` idiom (runner_systemd.go): job `done` = exit 0; otherwise the unit stays loaded as `failed`, `ExecMainStatus`/`Result` are read, then it is reset. No pipes, no `SuccessExitStatus=`, no name patterns. Every unit gets `BindsTo=` the orchestrator's own service when there is one [M8]; the exact names started are recorded, and swept at the next start. A cancelled context stops the unit and *confirms* it gone. | root |
| `plan` | Subcommand `plan`, run inside unit **P**: adapts `/etc/hotserve/Caddyfile` with `/usr/bin/hotserve adapt`, twice when the Caddyfile or its imports hold a `{$NAME}` — empty environment, then each name set to a sentinel — and refuses, naming the variable, when `root` or any `backup` block differs. Prints a strict plan: root, and per app its declaration. Root parses that with `DisallowUnknownFields` and **re-validates all of it** (`backupdecl.Validate`, the app-name alphabet, root absolute and clean). | `DynamicUser=` |
| `dump` | Subcommand `dump`, run inside unit **A**. Per declared database: open under an `os.Root` of the shared dir with `O_NOFOLLOW|O_NONBLOCK`, `fstat` regular, SQLite header [M1]; `sqlite3 -cmd ".timeout …" <db> "VACUUM INTO …"` into staging at the same relative path; `integrity_check` on the copy — ok means exit 0 **and** output exactly `ok` [H]. | `hotserve`, user+PID namespaces, no network |
| `engine` | The run: lock → sweep recorded units → P → per app: `lstat` the shared dir itself (absence is decided here, never inside a sandbox; only `ENOENT` is absence) → A → B (`restic backup --quiet --json --retry-lock … --host hotserve --tag app:<name> /backup/<app>`) → verify → C. B's verdict needs exit 0, a 64-hex `snapshot_id` from the summary file [M12], and every declared item found by `ls <id>` on the item's parent [H]. | root |
| `record` | `status.json`: per app the last run's class, snapshot id, what was verified, when. Atomic write, root-owned, no secrets. PR 4's `status` reads it. | root |

**What reaches unit A and B.** Never argv, never environment: a root-written plan file for that one app, bound read-only at a fixed path. Declared sub-paths are bind sources as typed structs [M9]; B sees `files` items at `/backup/<app>/files/<item>` and the staged copies at `/backup/<app>/sqlite/<item>`, so a declared database inside a `files` path is simply never bound in its live form — failure mode 7 closed by the view, not by an exclude pattern. *To measure first:* binding a sub-path whose parent is not bound, and the view when `files .` is declared together with a database (the live file and its sidecars then need masking: `InaccessiblePaths=` inside a bind, or restic `--exclude-file` written by root — measure both, pick the one that fails closed).

**The FIFO swap, and the one bound there is.** Given a path, the `sqlite3` shell blocks for ever on a FIFO [M1], and the app can swap one in between `dump`'s checks and the open — which, unbounded, would end every app's backups on the box. The `ATTACH … ?mode=rw` form [M18] fails at once on a socket, a directory and an ordinary FIFO and never creates a missing file, but a FIFO made mode 0400 still blocks it [M19]. So the *open* — not the copy — has a bound: if the copy's target file has not appeared within 5 minutes (it appears in ~11 ms, whatever the size; a lock wait of up to 30 s comes first [M20]), `sqlite3` is killed by `dump`, its own parent, and that database is reported `never opened`. **D4, final for the dump: no bound on copying, uploading, restoring or checking; one bound, on opening a database.** Agreed by the owner 2026-09-19.

**Failure-path e2e, written before the happy path** (each shown failing once): wrong password (12) · no repository (10) · repository locked by a running `check` (11 → waits with `--retry-lock`, succeeds) · unreachable host (class `unreachable`, not `damaged`) · FIFO / device / symlink / empty file declared as a database · FIFO swapped in mid-run · a declared path that vanishes (exit 0 [M11] → caught by the `ls` check) · shared dir missing, never backed up → `pending`; missing after a good backup → `error: data missing` · `${RESTIC_PASSWORD}` and `{$VAR}` as a root/path · orchestrator SIGKILLed mid-upload → unit gone, staging emptied by the next run · two runs at once → second says who holds the lock · a symlinked liveswap root · two apps, then the documented `forget` policy run against the repository: each app keeps its own history.

**Fixture.** `rclone serve s3`, static binary from rclone's image pinned by digest into `FROM scratch` [H]; its own compose service; the suite runs as a **parallel** CI job (costs its length plus the build, not the e2e job's critical path [H]). gitleaks: fixture keys get an allowlist entry by text [H].

### Deferred until #139 is merged (owner, 2026-09-19): how the upload unit is shown an app's data — D11

Raised by an experienced reviewer: the mount machinery (root pins each declared path and bind-mounts it itself; `CAP_SYS_ADMIN`, host mount namespace, a sweep for leftover mounts, never-recurse removal) exists because a *different uid with a read capability* reads the app's data while *systemd resolves bind sources as root, following links*. Decide between, **before PR 3** (restore writes into the same app-replaceable `shared/` and should be built on whichever mechanism stays) and **before PR 4** (it fixes what the run's service needs):

| | A (as merged) | B identity check | C one mount | D no capability |
|---|---|---|---|---|
| What | pin + mount each declared path | bind whole `shared/` by path; root-written restic file with negated patterns selects declared paths; upload unit's fixed wrapper compares `/backup/<app>/files`' dev+inode with what root `fstat`ed (fd held open for the run) before exec'ing restic | whole `shared/`, one engine-made mount per app, same restic file | upload as `hotserve` in a user namespace, **no `CAP_DAC_READ_SEARCH`**; whole `shared/` by path; same restic file |
| Run needs `CAP_SYS_ADMIN` | yes | no | yes | no |
| T5 re-aims `shared/` at `/etc` → root's secrets via restore | closed | closed | closed | not applicable: reads only what `hotserve` can |
| Credential kept from T5 by | separate uid | separate uid | separate uid | user namespace only [H: measured] |
| Our code in the credentialed unit | no | yes | no | no |

**Measured for this decision:** from inside liveswap's sandbox view an app **cannot** rename, remove or replace `<root>/<app>/shared`, nor create anything beside it ("Read-only file system" each time; writing inside `shared/` works) — so for T1 a by-path bind of the whole `shared/` has no race. **T5 can** re-aim it (it owns `<root>/<app>`, outside any sandbox), and with the read capability that is `hotserve` → `backup.env` / `/etc/shadow` into a snapshot and back out through a restore: the pin was also what kept the capability from being a way up for T5. **To measure before building any of B/C/D:** restic negated exclude patterns (`/backup/blog/files/*` + `!/backup/blog/files/uploads`, nested and awkward names, so the snapshot's path stays `/backup/<app>` and retention groups do not change with the declaration); for B, the identity check under a toggler run *as T5 would*, outside any sandbox; for D, that the user namespace closes `/proc/<pid>/environ` for the exact upload unit. Dropped: ACLs on `shared/` (an app's 0600 files mask them; changes app data); idmapped bind mounts (unknown whether systemd 257 offers them to services). The dedicated account stays whatever is chosen: restore's fetch step cannot run in a user namespace [H: `lchown` EINVAL].
My lean: D if the user namespace is an acceptable sole shield for the credential during uploads; else B.

### Deferred with D11 (owner, 2026-09-19): where a declaration lives — D12

Raised by the owner after Copilot's second review of #139 found that `{$NAME}` substitution is textual, so a value with a newline in it is more lines of Caddyfile [measured: `CMD` = `./server`, newline, `backup { files . }` gives the server's app a declaration that is nowhere in the file; a space gives `command` two arguments]. One-token placeholders cannot show that no value restructures the file, and a run does not know the server's values. As merged, that is a documented limit (#139, `0b1e0f6`): a declaration that exists only through the server's environment is not backed up, and nothing says so. The environment is root's to write, so it is not an attack path.

**The option: declarations leave the Caddyfile.** A small root-owned file (say `/etc/hotserve/backup.conf`: the liveswap root, and per app its `sqlite` / `files` paths, validated by `backupdecl`'s rules; no substitution, no imports, no adapter), written through the same sudoers-gated push as the Caddyfile and validated by the engine as now.

| | Caddyfile + placeholders (as merged) | Separate file |
|---|---|---|
| Declaration sits in the app's own block | yes | no |
| "No second config format" [H §4] | kept | **broken** |
| A new app added with no backup lines | seen while writing the block | silent unless cross-checked |
| Liveswap `root` written once | yes | twice — can drift |
| `hotserve validate` / `bin/push` reject a bad declaration | yes | only through `hotserve-backup check` in `bin/push` (planned for PR 4 anyway) |
| Heuristics decide what gets backed up | **yes** | no |
| Goes away | — | `hotserve adapt`, the plan unit, placeholders, the trial, import scanning, every `{$NAME}` limit, Copilot's structural gap, PR 1's liveswap change (the serving binary then knows nothing of backups), `plan/make.go` |

**The reframing that matters.** Today adapt is *authoritative*: when its heuristics are wrong, the wrong thing — or nothing — is backed up. With a separate file adapt can stay as an *advisory* cross-check in `status` / `check` ("app `shop` is in the Caddyfile and declares no backup"; "the Caddyfile's root is X, the backup file says Y"): the same heuristics, failing in the safe direction — a lost warning, not a lost backup — and it answers the two real costs (the forgotten app, the drifting root).

My view: on robustness the separate file with an advisory cross-check is the better design; against the handover's stated goal ("two/few config lines per app … the operator never thinks about backups again", lines in the app's block) it is a product decision, the owner's. Rework is moderate and mostly deletion: remove PR 1's liveswap declaration, replace `plan` with a file parser, move `backupdecl` into the backups module, add the cross-check; engine, units, dump, verify and the e2e suite barely change. Also on the table, smaller: keep the Caddyfile and (2) refuse any `{$NAME}` inside the `liveswap` block once any app declares a backup — a new limit on configs that work today (`command {$CMD}`, `env KEY {$VALUE}`), and not complete (a value outside the block could in principle inject one); or (1) leave it as the documented limit, with PR 4's `check` warning about a `{$NAME}` inside the `liveswap` block.

**Decide with D11, after #139 merges and before PR 3 and PR 4:** it changes what PR 4's `setup` / `check` / `bin/push` wiring is, and both reshape the same code.

### Found while building PR 1

- **`{$VAR}` is invisible to liveswap.** The D7 limit holds for `{env.X}`, which liveswap sees as written (the check runs in `Provision`, before the root is resolved in place — `TestProvisionChecksTheRootBeforeResolvingIt`). The Caddyfile's *adapt-time* form, `{$VAR}` / `{$VAR:default}`, is substituted in the raw text before any module sees a token, so the serving process cannot refuse it — and the plan unit **P** adapts with an empty environment, so `root {$LIVESWAP_ROOT:/var/lib/liveswap}` would give the backup job a different root from the server's, reported as "no data yet". Closed in PR 2, in P: adapt twice — once with an empty environment, once with every `{$NAME}` found in the Caddyfile and its imports set to a sentinel — and refuse when the two disagree on `root` or on any `backup` block, naming the variable. Test first: that exact config, asserted to fail loudly rather than report `pending`. And `status` always prints the full path it looked at.
- **The declaration's own input grammar** refuses a path that is not UTF-8 (the JSON it travels in cannot spell it) or holds a control character (it is printed in logs and status). Both are limits on a new input, not on anything that works today; listed here because the project discusses limits first.
- *Aside, not this feature's to change:* liveswap sends an app's `command` as plain `ExecStart` (go-systemd's `PropExecStart`), so systemd expands `${VAR}` in it from the unit's environment, `env_file` values included [M9]. The operator writes both, so it is not an escalation, but it is probably not known.

One limit stands: an app that declares a `backup` while `root` or a backup item is written with a placeholder (`{env.X}`) is rejected by `hotserve validate`, naming the fix. - **D4 — time bounds: delegated to me. Decision: no manager-enforced bound on any unit.** restic bounds its own waiting [M10]; a person waiting is told what for after 30 s and Ctrl-C stops the exact units the run started; a wedge shows in `status`, which judges freshness from the last complete snapshot whatever is "in progress" and names the running phase and since when.
  What would change it, and when it is looked at — all before `backup` merges, so nothing is left as a follow-up:
  1. PR 2: restic's retrying on a wrong secret does **not** end by itself (watched to the end against the fixture) → query units get a backstop at twice the longest ending measured.
  2. PR 2/3: any failure-path e2e that finds a unit outliving its purpose with no operator present to press Ctrl-C.
  3. PR 5: the tens-of-GB measurement. If a legitimate `snapshots`/`ls` there is far below any candidate backstop, a backstop costs nothing and goes in; if it is close, it stays out.
